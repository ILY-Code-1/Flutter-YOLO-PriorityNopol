Desain Basis Data Relasional (ERD → LRS) — PrioScan

PrioScan — Priority Vehicle Scanner using YOLOv8. Dokumen ini memodelkan ulang data deteksi kendaraan prioritas ke dalam skema relasional ternormalisasi, sebagai padanan konseptual dari penyimpanan Firestore. Catatan deteksi Firestore dinormalisasi menjadi tiga entitas: VehicleType, Detection, dan DetectionImage.

Catatan render: seluruh kode PlantUML berada di dalam tag <pre class='plantuml'> agar dapat di-render manual (mis. melalui plantuml.com atau ekstensi PlantUML).

1. Entity Relationship Diagram (ERD)

Terdapat tiga entitas utama:

  • VehicleType — master jenis kendaraan prioritas (Ambulance, Police, Fire Truck). Satu jenis kendaraan dapat muncul pada banyak deteksi.
  • Detection — catatan satu peristiwa deteksi (nomor polisi, waktu, confidence). Mereferensi satu VehicleType.
  • DetectionImage — gambar base64 dari sebuah deteksi, dipisah dari Detection karena ukurannya besar. Berelasi satu-ke-satu dengan Detection.

Relasi: VehicleType 1 — N Detection (satu jenis dimiliki banyak deteksi); Detection 1 — 1 DetectionImage (setiap deteksi memiliki tepat satu gambar). Tidak terdapat relasi many-to-many pada domain ini.

2. Transformasi ERD ke LRS (Logical Record Structure)

Berikut keputusan transformasi tiap relasi dari ERD menjadi struktur tabel logis:

  • Relasi 1—N (VehicleType → Detection): Foreign Key diletakkan pada sisi many, yaitu kolom vehicle_type_id ditambahkan ke tabel Detection yang mereferensi VehicleType.vehicle_type_id.
  • Relasi 1—1 (Detection → DetectionImage): Karena DetectionImage memiliki partisipasi total terhadap Detection (gambar tidak ada tanpa deteksi), FK ditempatkan pada sisi DetectionImage. PK tabel DetectionImage sekaligus menjadi FK ke Detection.detection_id (shared primary key), sehingga relasi 1—1 terjamin.
  • Relasi Many-to-Many: tidak ada pada domain ini, sehingga tidak ada tabel junction yang dibuat.
  • Atribut multivalue / weak entity: tidak ada; seluruh atribut bernilai tunggal.

Hasil transformasi menghasilkan tiga tabel: vehicle_type, detection, dan detection_image.

@startuml
class "vehicle_type" <<Table>> {
  + PK vehicle_type_id : INT
  - code : VARCHAR(20)
  - name : VARCHAR(30)
}

class "detection" <<Table>> {
  + PK detection_id : BIGINT
  # FK vehicle_type_id : INT  -- ref vehicle_type
  - plate_number : VARCHAR(15)
  - detected_at : DATETIME
  - confidence : DECIMAL(4,3)
}

class "detection_image" <<Table>> {
  + PK detection_id : BIGINT  -- shared key (1:1)
  # FK detection_id : BIGINT  -- ref detection
  - image_base64 : LONGTEXT
  - mime_type : VARCHAR(20)
}

"vehicle_type" --> "detection" : 1 .. N (FK vehicle_type_id)
"detection" --> "detection_image" : 1 .. 1 (FK detection_id)
@enduml

3. Logical Record Structure (LRS) — Final

Struktur logis final setelah transformasi, bersih tanpa anotasi proses:

@startuml
class "vehicle_type" <<Table>> {
  + PK vehicle_type_id : INT
  - code : VARCHAR(20)
  - name : VARCHAR(30)
}

class "detection" <<Table>> {
  + PK detection_id : BIGINT
  # FK vehicle_type_id : INT
  - plate_number : VARCHAR(15)
  - detected_at : DATETIME
  - confidence : DECIMAL(4,3)
}

class "detection_image" <<Table>> {
  + PK FK detection_id : BIGINT
  - image_base64 : LONGTEXT
  - mime_type : VARCHAR(20)
}

"vehicle_type" "1" --> "0..*" "detection"
"detection" "1" --> "1" "detection_image"
@enduml
